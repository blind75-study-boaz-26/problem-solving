# 과제 제출 가이드

매주 **md 파일 하나**를 PR로 제출합니다. 이 문서는 그 파일에 무엇을 담아야 하는지, 그리고 왜 그것을 담는지를 정합니다.
복사해서 바로 쓰는 양식은 [주간 제출 템플릿](../templates/weekly-submission.md)에 있습니다.

---

## 이 과제의 목적

문서를 남기는 이유는 기록 자체가 아닙니다. 목적은 두 가지입니다.

1. **문제를 보고 패턴을 떠올리는 능력을 키운다.** 코딩 테스트에서 실제로 쓰이는 능력은 "이 문제는 투 포인터다"를 5분 안에 판단하는 것입니다. 정답 코드를 보관해도 이 능력은 안 자랍니다. 판단의 근거를 글로 쓸 때 자랍니다.
2. **수요일 화이트보드 세션을 그대로 소화한다.** 세션에서 요구하는 네 가지 — 입출력 분석 / 자료구조 선택 근거 / 시간·공간 복잡도 / 엣지 케이스 — 를 템플릿의 필수 항목으로 그대로 넣었습니다. **과제를 쓰면 그게 곧 발표 대본입니다.** 따로 준비할 게 없게 만드는 것이 이 설계의 목표입니다.

그래서 지켜야 할 원칙이 하나 있습니다.

> **한 문제당 10분 이내에 쓸 수 있어야 한다.**
>
> 과제가 무거워지면 아무도 5문제를 풀지 않습니다. 필수 항목은 대부분 한두 줄짜리입니다.
> 길게 쓰는 게 잘 쓰는 게 아닙니다. 판단의 근거가 한 문장으로 적혀 있으면 그게 잘 쓴 것입니다.

---

## 필수 항목 (8개)

각 문제마다 아래 8개를 채웁니다. 괄호 안은 분량 기준입니다.

### 1. 메타 정보 (1줄)
문제 링크, 난이도, 사용 언어, 그리고 **결과 태그**.

결과 태그는 셋 중 하나입니다: `자력해결` / `힌트봄` / `해설봄`

> **왜 필요한가:** 이걸 숨기면 문서가 쓸모없어집니다. 전부 `자력해결`로 채워진 문서는 복습할 때 아무 정보도 주지 않습니다. `해설봄`이라고 정직하게 적힌 문제가 곧 다음 달에 다시 풀어야 할 문제입니다. 벌금은 목표 문제 수 미달에만 부과되므로, 이 태그를 솔직하게 써서 불이익 받을 일은 없습니다.

### 2. 입출력 정리 (1~2줄)
입력의 **제약 조건**(배열 길이 범위, 값의 범위, 음수/중복 허용 여부)과 출력의 형태.

> **왜 필요한가:** 제약 조건이 알고리즘을 결정합니다. n이 10⁵면 O(n²)은 탈락이고, 값이 음수를 포함하면 Maximum Product Subarray의 접근이 완전히 달라집니다. 문제 풀이의 첫 단계는 코드가 아니라 이 제약을 읽는 것입니다.

### 3. 접근 (3줄 이내)
브루트포스 아이디어 → **왜 부족한가** → 최종 아이디어 한 문장.

> **왜 이 3단 구조인가:** 면접에서 실제로 이렇게 말해야 합니다. 최적해를 바로 꺼내는 사람은 "외웠구나"로 보이고, 브루트포스에서 개선 근거를 밟아 올라가는 사람은 "생각할 수 있구나"로 보입니다. 최적해를 이미 안다고 해도, 어떤 병목을 없앤 것인지 한 줄로 쓰세요.

### 4. 자료구조·알고리즘 선택 근거 (1~2줄)
왜 배열이 아니라 해시맵인지, 왜 정렬을 먼저 했는지, 왜 스택인지.

> **왜 필요한가:** 화이트보드 세션의 필수 항목입니다. 그리고 이 질문에 답할 수 없으면 그 풀이는 아직 내 것이 아닙니다.

### 5. 복잡도 (1줄)
시간·공간 복잡도와 **한 줄 근거**. `O(n log n) — 정렬이 지배적` 처럼 씁니다.

> **왜 근거까지 쓰는가:** `O(n)`만 적으면 맞는지 틀리는지 아무도 모릅니다. 어느 연산이 지배적인지 지목할 때 비로소 이해한 게 드러납니다.

### 6. 엣지 케이스 (최소 2개)
각각 **어떻게 처리했는지**까지 씁니다. 빈 입력, 원소 1개, 전부 같은 값, 음수/0, 오버플로, 정답이 없는 경우 등.

> **왜 최소 2개인가:** 하나만 쓰라고 하면 아무 생각 없이 "빈 배열"만 씁니다. 두 개를 강제하면 문제 고유의 함정을 찾게 됩니다.

### 7. 코드 (원본 그대로)
언어 태그를 붙인 코드 블록에 제출한 코드를 그대로 붙입니다. 정리하거나 주석을 추가하지 마세요.

> **왜 원본인가:** 나중에 다듬은 코드는 "그때 내가 실제로 쓴 코드"가 아닙니다. 변수명이 엉성했다면 그것도 정보입니다.

### 8. 다시 볼 때의 트리거 (1문장)
**"이 문제를 두 달 뒤에 다시 만나면 무엇을 떠올려야 하는가"** 를 한 문장으로.

예: *"정렬된 배열에서 두 수의 합 → 양끝 투 포인터"*, *"원형 배열 DP → 첫 원소 포함/제외 두 번 돌리기"*

> **왜 이게 가장 중요한가:** 8개 중 하나만 남겨야 한다면 이걸 남기겠습니다. 나머지 항목은 "내가 이 문제를 이해했다"는 증거지만, 이 한 문장은 **다음번에 회수할 수 있는 자산**입니다. 75개가 모이면 그것이 여러분의 패턴 사전이고, 학기 말에 가장 많이 읽게 될 문서입니다.

## 선택 항목 (권장)

부담되면 생략해도 됩니다. 다만 둘 다 실제로 효과가 큽니다.

- **막힌 지점 / 소요 시간** — 어디서 몇 분을 썼는지. 30분 넘게 막혔다면 그 지점이 진짜 약점입니다.
- **`복습 필요` 체크박스** — 표시해 두면 학기 말에 grep 한 번으로 개인 복습 리스트가 나옵니다.

## 주차 파일 맨 앞에 쓸 것

문제별 내용 앞에, 그 주차의 요약을 짧게 씁니다.

- **선언한 목표 문제 수 / 실제로 푼 문제 수** — 정산의 근거가 됩니다.
- **패턴 태그 한 줄** — 예: `#투포인터 #해시맵 #슬라이딩윈도우`. 나중에 grep으로 "투 포인터 쓴 문제 전부" 를 찾을 수 있습니다.
- **한 줄 회고** — 이번 주에 새로 알게 된 것 한 가지.

## 제출 규칙

### 파일 위치와 이름

```
submissions/
  W02/
    wsxchoi.md      ← (github id)
  W03/
    ...
```

> 한글 파일명은 OS·터미널 환경에 따라 인코딩이 깨질 수 있으니 영문 GitHub 아이디를 씁니다.
> 파일 안 제목에는 한글 이름을 쓰면 됩니다.

### 브랜치와 PR

| 항목 | 규칙 |
|---|---|
| 브랜치 | `w02/wsxchoi` |
| PR 제목 | `[W02] 최우성 - 5문제` |
| 마감 | 해당 주차 **수요일 20:00 (세션 시작 전)** 까지 PR open |
| 머지 | 세션 종료 후 팀장이 머지 |

PR 본문에는 "선언한 목표 / 실제 푼 수" 만 적으면 충분합니다. 내용은 md 파일에 있습니다.

### 코드를 md 안에만 두는 이유

별도 소스 파일을 만들지 않고 md 코드 블록에만 넣습니다. 사고 과정과 코드를 한 화면에서 같이 읽을 수 있어야 리뷰가 되기 때문입니다. 대신 코드를 돌려볼 수는 없으니, **제출 전에 LeetCode에서 Accepted를 받은 코드만 붙입니다.**
